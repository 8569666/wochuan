# 首批开发设计：可运行的总部后台与基础档案

日期：2026-10-15。状态：用户已审核通过（2026-10-15）；尚未开始产品代码实施。

## 1. 目标、约束与成功标准

用户已选择由自己主导、AI协助开发，首批完成基础档案，再接采购库存。
用户指定 Python 3.14 和本地 MySQL，取代原PRD中的 Python 3.12/PostgreSQL。
所有项目文件放在 D:\Codex\wochuan，使用现有 Git 仓库。
已实测本地 Python 3.14.7、MySQL 8.0.46、codex_db、utf8mb4；数据库当前没有表。
连接配置已有 DB_CONNECTION、DB_HOST、DB_PORT、DB_DATABASE、DB_USERNAME、DB_PASSWORD，文件为根目录 .env，不进入版本库。

成功标准：用户能够启动前后端、登录后台、建立一个总仓和两家门店、维护供应商、创建一款3色4码商品并生成12个持久化SKU；刷新及服务重启后数据仍然存在。

本批不包含采购订单、库存变动、支付、POS、打印、离线同步、会员、提成、加盟结算及BI。门店类型保留直营/加盟/联营字段，但不实现后两者结算。

## 2. 方案与工程结构

采用模块化单体：Vue 3 + TypeScript + Vite + Pinia + Element Plus 前端，FastAPI + Pydantic v2 + SQLAlchemy异步后端，MySQL InnoDB数据层，Alembic维护迁移。
异步驱动选择 aiomysql，并在实施首项验证 Python 3.14 安装、导入、连接及SQLAlchemy异步事务；依赖使用支持3.14的稳定版本并记录可复现锁定结果。
前后端分别放在 frontend/ 与 backend/；根目录提供Windows启动说明和脚本，后端使用独立 .venv，前端使用 npm 及 package-lock.json。
本批不引入Redis、任务队列或额外数据库服务；直接连接现有MySQL。

备选方案：只做静态原型无法验证数据库闭环；首批同时做采购库存会扩大业务规则和测试范围。因此选择用户已确认的真实基础档案后台。

开发入口为 http://127.0.0.1:5173，后端为 http://127.0.0.1:8000，Vite代理 /api；默认仅监听本机。
后端健康检查区分进程存活与数据库就绪。数据库断开时就绪检查失败，并向页面返回可理解的错误；页面不能把查询失败显示为零条数据。

## 3. 登录、权限与界面

本批提供一个总部管理员角色与管理员账号初始化命令，不实现开放注册、用户管理或自定义权限编辑。
初始化命令交互录入密码，不设公开默认密码、不写入文档或Git，重复执行不覆盖已有账号。
密码用Python标准库scrypt加独立随机盐存储；登录产生高随机性会话令牌，数据库仅存令牌摘要、用户及有效期。
会话有效期8小时，通过HttpOnly、SameSite=Strict Cookie传递；生产HTTPS启用Secure。退出立即撤销会话，停用用户不能继续访问。
所有业务接口由后端校验用户和管理员权限，前端路由限制只用于交互。状态变更请求校验Origin与配置的站点地址，开发代理保持同源。
登录失败统一提示，加入失败次数限流；日志不记录密码、会话Cookie或数据库连接密钥。

中文桌面后台导航：工作台、门店管理、仓库管理、供应商管理、商品中心。
工作台显示数据库实际统计的门店、仓库、供应商、款号、SKU数量与快速入口，不伪造经营指标。
布局使用固定侧栏和清晰的内容区，统一列表搜索、分页、创建/编辑弹窗、停用确认、加载/空白/失败状态。商品矩阵使用独立编辑区，避免大表单挤在弹窗里。
所有提交期间禁用重复点击；失败保留已填写内容；首次安装显示初始化说明，不自动注入样例业务数据。

## 4. 基础档案与数据规则

数据表以 werp_ 前缀命名；迁移版本表也使用专属前缀。主键统一BIGINT自增，表名使用小写。
所有表使用InnoDB与utf8mb4；金额使用DECIMAL(12,2)，接口使用十进制字符串，禁止浮点计算。
时间使用DATETIME(6)并统一存储UTC，界面按Asia/Shanghai显示。SQLAlchemy统一管理提交和回滚，不依靠缓存维持主数据。
编码去除首尾空白并统一大写，由数据库唯一约束保证并发时不重复；更新时排除当前记录。错误回滚后返回中文冲突提示。
用户、会话、门店、仓库、供应商、颜色、尺码组、尺码、SPU、SKU及操作审计是本批实体。
档案提供创建、查询、编辑、启停用；不提供业务档案物理删除。被引用的颜色和尺码不能改编码；已生成的SKU编码、条码、颜色尺码组合不随主档案编辑而自动改写。

门店：编码、名称、类型、地址、联系电话、状态；区域首批为可选文本，不建立多级组织编辑模块。
仓库：编码、名称、类型、关联门店、状态。类型为总仓、店仓、在途、残次；店仓必须绑定门店，其他类型不能绑定门店，每家门店最多一个默认店仓。创建门店不会隐式创建仓库。
供应商：编码、名称、联系人、联系电话、地址、结算方式、备注、状态。首批维护信息，不计算应付或评分。
颜色：编码、名称、可选十六进制色值、状态；尺码组含名称、编码、排序后的尺码项。颜色与尺码编码仅允许英文字母、数字和下划线，保证组合编码可识别。

SPU：唯一款号、款名、品类文本、年份、季节、波段、面料、安全类别、吊牌价、采购基准价、最低零售价、状态。品牌及类目树管理留待后续，首批使用基础文本字段。
创建时选择颜色及一个尺码组，预览笛卡尔积矩阵，可批量填写SKU零售价及条码。
SKU编码为“款号-颜色编码-尺码编码”；缺省条码使用相同内部编码，可用于后续Code-128打印，不声称生成合规EAN-13编号。
SKU全局编码、条码唯一；SPU内颜色尺码组合唯一，条码非空，价格非负，款号/编码使用ASCII字母数字及约定分隔符。
SPU与全部SKU一次提交同一事务；任一SKU冲突全部回滚。重复请求产生明确冲突，不生成第二套商品。
第一批商品创建后允许编辑名称、描述、价格和启停用；颜色尺码矩阵及编码只读。新增规格与历史单据兼容规则在采购模块接入前另行设计。
采购基准价只是档案参考价，不标记为移动加权成本；第一批没有库存编辑入口，也不创建虚假库存。
审计记录操作者、动作、对象、时间与必要的变更字段，不记录敏感凭据。

## 5. 接口与数据流

所有业务接口以 /api/v1 开头，响应沿用PRD的 code/message/data/timestamp；HTTP状态与业务结果一致，错误不统一伪装成HTTP 200。
认证接口：POST /auth/login、POST /auth/logout、GET /auth/me。
档案接口：/stores、/warehouses、/suppliers、/colors、/size-groups，各自支持GET列表/详情、POST创建、PATCH编辑；启停用通过PATCH状态。
商品接口：GET/POST /products，GET/PATCH /products/{id}；GET /products/{id}/skus。创建请求包含SPU字段、颜色ID、尺码组ID及矩阵规格价格/条码。
矩阵预览由前端基于字典生成，后端独立验证颜色尺码与完整组合，不能只信任前端预览。商品查询支持款号、名称或条码搜索。
列表使用关键词、状态、页码和页大小查询，默认20条、最多100条，返回items、total、page、page_size。
输入错误为422、未登录为401、权限不足为403、找不到为404、编码条码冲突为409；数据库异常返回通用服务错误和请求标识，不返回堆栈或连接串。
通过OpenAPI导出契约，为前端生成或维护一致的TypeScript类型，避免同一字段两端定义不一致。

## 6. 迁移、测试、交付与开发管理

迁移只创建/维护werp_项目表，不drop数据库、不操作其他表；初始化前核对目标库与现有表冲突。没有表时执行首个迁移，重启不重复建表。
集成测试使用独立测试库及明确测试环境标识，绝不清空codex_db。创建测试库权限不足时报告并保留开发库，不用SQLite替代MySQL行为验证。
自动验证覆盖登录退出及会话过期、未登录访问、字典校验、重复编码条码、店仓绑定、商品12SKU生成、SKU失败整单回滚和中文数据持久化。
前端验证覆盖登录、导航、创建编辑停用、搜索分页、矩阵批量输入、错误保留输入以及刷新后持久化；补充真实浏览器操作，并检查控制台错误和主要页面截图。
依赖兼容性、迁移、后端测试、前端类型检查/构建和浏览器验收均有实际结果后才能报告完成；未通过的检查明确列出。
提供.env.example（无真实凭据）、启动停止方法、迁移与管理员初始化步骤、验收步骤；依赖锁文件和迁移文件提交Git。
